## D46: U27 - the arm decides the published name; the layer publishes STRICT and does not override a consumer's `NO_STRICT` (11 Nov 2026), CLOSES U27

Decision (user, 11 Nov 2026): U27 closes as a **recorded policy decision, no code change**. The invariant now in force:

> **The QOR Windows api_layer publishes the `STRICT` arm, and does not override a consumer's `NO_STRICT`.**
> `HOOKPROC` is published as the SDK's typed `CALLBACK`, and every `DECLARE_HANDLE` type (`HWND`, `HHOOK`,
> `HINSTANCE`, `HBITMAP`, `HRGN`, `HICON`, …) as its opaque struct pointer. A consumer of this layer builds in
> the same arm as the layer builds in, which is the SDK default; a consumer that opts out with `NO_STRICT` gets
> that arm's types and therefore that arm's published names, and the mismatch is recorded, not fixed.

That is the same shape as the two earlier library-side pins that refused to become build-wide defines: **D21**
pinned the version triple in `kernel32.h:22-30` with guarded `#ifndef`s plus a floor assertion and explicitly
left the third-party residual unfixed ("the pin is library-side, so it does not constrain third-party
consumers"); **D45** closed U26's `UNICODE` width axis with **no project-wide `/DUNICODE`**. U27 is the third
axis of the same family - the `STRICT`/`NO_STRICT` arm - and it closes the same way.

### The mechanism (read on disk, Windows Kits 10 `10.0.26100.0`, `C:\Program Files (x86)\Windows Kits\10\include\10.0.26100.0\`)

- `shared\minwindef.h:21-25` and `shared\ntdef.h:785-789` - both, in this order: `#ifndef NO_STRICT` → `#ifndef STRICT` → `#define STRICT 1`. So `STRICT` is on **unless** a consumer defined `NO_STRICT` before the first read of these headers.
- `shared\ntdef.h:851-861` - the arm switch itself: `:851` `#ifdef STRICT`, `:852` `typedef void *HANDLE;`, `:856` `#define DECLARE_HANDLE(name) struct name##__{int unused;}; typedef struct name##__ *name` (the `:853` `#if 0 && (_MSC_VER > 1000)` alternative at `:854` is dead code), `:858` `#else` with `:859` `typedef PVOID HANDLE;` and `:860` `#define DECLARE_HANDLE(name) typedef HANDLE name`. So under `STRICT` each handle is its **own** struct-pointer type and the handles do not interconvert; under `!STRICT` every `DECLARE_HANDLE` type **is** `void *` and they all interconvert. `:862` `typedef HANDLE *PHANDLE;` sits outside the switch and is arm-stable.
- `shared\windef.h:39-40` - `DECLARE_HANDLE(HWND);` and `DECLARE_HANDLE(HHOOK);`, outside the `NOMSG`/`NOWH`/`NOUSER` opt-outs but inside the `STRICT` switch.
- `um\winuser.h:119` - `typedef LRESULT (CALLBACK* HOOKPROC)(int code, WPARAM wParam, LPARAM lParam);` in the `STRICT` arm, against `um\winuser.h:162` `typedef FARPROC HOOKPROC;` in the `#else /* !STRICT */` arm opened at `:139`.

Under `STRICT` the handle types are **distinct** struct-pointer types; under `!STRICT` they are all `void *` and
interconvert. C++ mangling encodes the pointed-to type, so the published name of a member whose signature names
one of them moves with the arm.

### Why the `#undef NO_STRICT` at `kernel32.h:36` is not the fix

- **It is inert for this tree.** `NO_STRICT` is defined nowhere in the repository and no build input defines or
  undefines it, so `#undef NO_STRICT` on an undefined macro is silent and changes nothing; the tree is already in
  the STRICT arm (P1). The folder gate and the 122-source all-libraries gate come out **byte-identical**, and under
  the gate convention the *diff* is the signal - an edit that cannot produce a diff cannot be shown to fix anything.
- **It is order-dependent** (P4). A TU that reaches `<Windows.h>` before any QOR header has already expanded the
  `!STRICT` typedefs by the time `kernel32.h` runs its `#undef`, so it keeps `HHOOK`/`HWND` as `void *` and keeps
  the mismatch. That is exactly the third-party residual D21 measured and left unfixed and D45 refused to close
  with a build-wide define; a library-side include cannot constrain it, only assert about it.
- **It moves the failure rather than removing it** (P6). For a consumer that deliberately chose `NO_STRICT`, forcing
  the STRICT arm replaces U27's *link* symptom ("a consumer that defines `NO_STRICT` compiles against this header
  cleanly and ends with an unresolved external for a name that plainly matches it") with hard **compile** errors in
  that consumer's own code - `C2440` on the first handle it passes along.
- **It erases a knob the consumer set.** `#undef NO_STRICT` does not only select an arm: it deletes a macro the
  consumer's own later `#ifdef NO_STRICT` logic reads. D21's precedent is the opposite shape - guarded `#ifndef`
  pins plus a floor assertion that *asserts* rather than clobbers. P7 shows the arm can be forced by `#define STRICT 1`
  without that damage, and it is still order-dependent, so it buys nothing that justifies the edit.
- **The arm-stable alternative is ruled out by decisions in force.** Retyping the affected parameters away from the
  STRICT-sensitive SDK types (e.g. `void *`, `FARPROC`) makes the published name arm-stable but breaks **D18**
  ("a wrapper's published signature is the SDK prototype of the export it binds") and **D25**, which typed the
  Desktop / Window Station callback parameters as the SDK's W spellings. The folder's convention is to copy the SDK
  spellings verbatim.
- **There is nothing in the tree to fix.** 0 in-tree callers of the affected family, and every source in the build
  already compiles in the STRICT arm. U27 is a property of the published surface, not a defect this library performs.

### What D46 settles, and what it deliberately does not

- Settles: U27's open question ("does the arm decide the published name, and may a consumer build in the other one?")
  - the arm does, and the answer for consumers of this layer is **no**: they build in the layer's arm. The published
  `*T` surface stays the SDK's spelling; no mangled name moves; the import surface of `winqor_api_user` is unchanged.
- Does not settle, and stays a recorded residual: a third-party TU that defines `NO_STRICT` and reaches `<windows.h>`
  before any QOR header. It gets its own arm and its own names; the layer neither constrains nor repairs it. Same
  residual class as D21's and D45's.
- Does not touch any source: `kernel32.h` stays as it stands (its only `#undef`s remain `min`/`max` at `:39-40`,
  and `:36` stays the blank line above `#include <Windows.h>` at `:37`); `user32.h` stays 819 lines / 600 members /
  599 bindings; 0 of the folder's 54 sources touched; no token moved; **no gate run** (nothing to diff).
- `registers/p6-u27.md` gains **only** a head closure line; its instance text stays frozen history and is never
  appended to (protocol 7), and its cites stay exactly as the entry wrote them. **P6 stays open** on that same
  register - the close is of U27 alone, and no recorded fact in that entry is rewritten at this close.

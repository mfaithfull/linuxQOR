### Signatures - D18, and the header edit is therefore `static` only

All 7 declarations already copy the prototype of the export their member binds - types, parameter names and order - so the
header edit adds `static` and nothing else. Two SDK details are carried as the SDK states them and enforced nowhere here:
`PCRAWINPUTDEVICE` is `CONST RAWINPUTDEVICE*` at `um\WinUser.h:15308`, so the const is already in the type and **no U23-style
const-on-pointer move is owed** (unlike the five class-A sites D23 fixed); `_In_reads_(uiNumDevices)` at `:15349` is the SDK's
own statement that the element count and `cbSize` agree, which this layer forwards rather than checks. `_tmp_t9_9b_sal.ps1`
reads **0 `_Check_return_` over the 8 prototype blocks**, so a discarded failure is silent on both sides at once.

### Return conventions (U1/U2/U7) - the numeric half of the session-27 soundness test covers 6 of the 7

0 `Win32ErrorHandler` and 0 `CheckReturn` in this TU (U1/U2 policy, settled 29 Oct 2026). The return mix is **6 numeric**
(5 `UINT` counts and 1 `LRESULT`) **+ 1 `BOOL`**: every `UINT` is a count of records, bytes or devices, so 0 is a legal
answer at each of the 5, and `DefRawInputProc`'s `LRESULT` is the callback's own value - so the session-27 test ("only sound
where the SDK's failure value is not also a legal success value") bars a zero-check at all 6. `RegisterRawInputDevices` is
the one member whose `FALSE` is unambiguous, but the reason for it (an oversized `cbSize`, an unregistered window class) is
unreachable because this layer carries no `GetLastError` pass-through. `GetRawInputDeviceInfo`'s handle is `_In_opt_`, so a
`NULL` handle is a legal argument, not a wrapper defect. Every value comes back as the OS wrote it, which is what leaves a
swallowed SEH fault and a legitimate 0 indistinguishable to the caller (U7).

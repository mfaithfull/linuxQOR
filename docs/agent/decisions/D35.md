## D35: U7 - swallowing a caught SEH fault to a default return is accepted as-is - POLICY (10 Nov 2026)

`Library::Call` (`src/platform/os/windows/api_layer/library.h:44`-`63`) catches every SEH fault in `ExceptionFilterFunction` and falls through to `ret _{}; return _;` (`:61`), so a fault returns the default value for the return type (`0`/`nullptr`/`false`) - indistinguishable from a legitimate zero (U2). `voidCall` (`:66`-`86`) and `varCall` (`:108`-`128`) do the same. The user decision: **accept as-is, no code change** - a made behaviour decision in the same shape U2 ("accepted as-is"), U15 (D14), U16 (D21) and U28 (D17) were closed on.

Why it is not a defect at this layer (measured on the error machinery, nothing inherited): the swallow is reached only after `ExceptionFilterFunction:20`-`28` has already raised the fault through `serious(...)`. `serious(msg)` is `issue<Serious, const std::string&>(msg)`, which is `new_ref<Serious>(...)->Handle()` (`src/qor/flyers/issue/issue.h:151`), and Handle walks the flyer handler stack:

- **A handler resolves it** (`IssueHandler<T>::Handle` returns true - `handler.h:47`'s default returns false = "failure to resolve"): control returns to `ExceptionFilterFunction`, which returns `EXCEPTION_EXECUTE_HANDLER`, the empty `__except` block runs, and `Call` returns `ret _{}`. But the caller's own handler already ran on the raised `Serious`, with the exception code/address/flags/info logged at `library.h:20`-`26`. The caller therefore already knows the call failed and is free to ignore the returned value; the default value is never consumed as if it were a legitimate one.
- **No handler resolves it**: `Escalate()` walks up the severity chain, and per `docs/issues.md:24` an error of Warning-or-above is "eventually thrown as an exception and then cause[s] your program to terminate"; the terminal arms are `Fatal::Handle` -> `std::terminate()` (`src/qor/flyers/error/fatal.cpp:45`) and `errorreporting.cpp:109`. So the process aborts and `ret _{}` is never observed at all.

Either way the default return is never silently mistaken for a legitimate zero: a resolved fault is already known to its caller through the handler that ran, and an unresolved fault terminates. Distinguishing a fault from a legal 0 is therefore a caller-side / `winqor_gui` responsibility, not a defect in this layer.

What D35 does not do:
- No change to `library.h` - `Call`/`voidCall`/`varCall` keep their `__except` swallow and `ret _{}` fall-through. The shared-header all-libraries gate is **not** in play (no header edit).
- No `CheckReturn`/`returncheck.h` is introduced - that stays U2's settled "accepted as-is" policy (G6 in force). U8's `throw("Missing library function.")` null-`pFunc` path is untouched.
- U2's note "a legitimate zero and a swallowed SEH fault stay indistinguishable to the caller" stays true as a *description*; it is now bounded by this decision - the indistinguishability never reaches a caller that has not already seen the failure.

## D45: U26 - the note goes on the published mirrors; U26 closes as "cannot be fixed within winqor_api_user" (11 Nov 2026), CLOSES U26

Decision (user, 11 Nov 2026): U26's deliverable is **a note on each published `winqor_gui` mirror the layer feeds**, in
the same arm U22 closed on at D43 - the note lands where the error actually is, and the item closes as
**cannot be fixed within `winqor_api_user`**. Six comment blocks were written over five published headers, each one
naming the shape or the field that is wrong, the site that feeds it, and the fix that would belong there. **No token
moved**: no declaration, no initializer, no typedef, no build input changed, so no gate is in play. No fact in
`registers/u26.md` is re-measured at this close - the entry's cites are carried into the notes exactly as written
(protocol 7: `u26.md` is frozen provenance and is never appended to).

### The artefacts (5 headers, 6 comment blocks)

- `src/platform/os/windows/ui/gui/gdiobjects/icon.h` above `IconInfoEx` - the **corruption** instance: `winuser.h` declares
  `ICONINFOEX` twice (A shape 560 bytes, W shape 1,080), the arm picked by `UNICODE`/`_UNICODE`, whose only source in this
  tree is `kernel32.h:7-10` under `qor_pp_unicode` (`configuration.h:13` = 1). The layer publishes `::PICONINFOEX`
  (`user32.h:442`) and `qor_pp_useswinapiAW` pastes `GetIconInfoExW` unconditionally, so a narrow TU compiles the 560-byte
  shape against a 1,080-byte write at `icon.cpp:94` - 520 bytes past the caller's struct, no compile error, no link error.
- `src/platform/os/windows/ui/gui/controllers/s_s/scrollbarcontroller.h` above `ScrollInfo` - layout verified sound
  (28 bytes, seven offsets identical on both arches, no character field so no width axis); the defect is that `nPos`
  and `nTrackPos` have no initializer and `SetScrollInfo` (`user32.h:647`) **reads** both.
- `src/platform/os/windows/ui/gui/controllers/windowcontroller.h` above `WindowPlacement` - 44 bytes, offsets identical
  both arches, but `length` has no initializer while `Get`/`SetWindowPlacement` (`user32.h:176`, `:206`) require
  `lpwndpl->length == sizeof(WINDOWPLACEMENT)` (`winuser.h:4768`, `:4775`); `GetPlacement`/`SetPlacement` have 0 in-tree
  callers, so latent.
- `src/platform/os/windows/ui/gui/view/handlers/message.h` above `Message` - the mirror is ABI-correct on x64 only
  (48 = 48; on x86 `MSG` is 28 and the mirror 40, divergent from `lParam` on), and `GetMessageT`/`PeekMessageT`
  (`user32.h:300`, `:307`) **write** the caller's buffer. Latent under D17.
- `src/platform/os/windows/ui/gui/controllers/i_m/monitor.h` - two blocks: above `MonitorEnumProc` (the fourth parameter
  is `long long` where SDK `MONITORENUMPROC` is `LPARAM`, 8 bytes against 4 on a 32-bit target, hidden by the cast at
  `monitor.cpp:187`) and above `MonitorInfoEx` (104 bytes = the W shape in the built tree, 72 = the A shape in the narrow
  world, while the entry point fills 104 - the `icon.cpp` overrun with the roles reversed).

### Why the fix is not in winqor_api_user's hands

- **The wrappers are already faithful.** Every signature the layer publishes for these members is the SDK prototype of
  the export it binds (`DispatchMessageT` takes `const MSG*`, `GetMessageT`/`PeekMessageT` take `LPMSG`,
  `GetIconInfoExT` takes `::PICONINFOEX`, `GetScrollInfo` takes `::LPSCROLLINFO`, `GetMonitorInfoT` takes
  `::LPMONITORINFO`) - D18's acceptance criterion. Nothing a wrapper does can change what a caller hands it: the caller
  reconstructs the payload type from a `winqor_gui` mirror and casts it.
- **The divergence is another library's surface.** `MonitorInfoEx`, `Message`, `IconInfoEx`, `ScrollInfo` and
  `WindowPlacement` are `winqor_gui` published headers (`qor_pp_module_interface(QOR_WINGUI)`); editing a field's width
  or adding an initializer there changes that library's published surface and behaviour, which the review phase records
  rather than performs - the standing U20 rule, the same arm U22 closed on at D43 and U19 at D41.
- **No hook, import entry or binding in this library can redirect the cast** a `winqor_gui` translation unit already
  performs into its own member function.
- The layer-side half is already settled by existing decisions: the api_layer's own include order is fixed by G1
  (`user32.h:7` includes `kernel32.h` before anything else), the A/W spelling by D13, and the version triple by D21.
  The published `*T` spelling therefore stays the SDK's, and a third-party TU that reaches `<windows.h>` before any
  QOR header still sees the narrow spelling of that surface - the **same residual D21 measured and left unfixed**
  ("the pin is library-side, so it does not constrain third-party consumers"). That residual is recorded, not fixed, and
  no project-wide `/DUNICODE` was added: `cmake/flags.cmake` still carries no `qor_pp`/`UNICODE` define (re-measured
  0 hits), so the width stays a source property and not a build behaviour decision for every consumer.

### What D45 does not do

- No `winqor_api_user` source changes: 0 of the folder's 54 sources, `user32.h` stays 819 lines / 600 members / 599
  bindings, coverage stays 724 of 1,018. No gate is run and both stay at their D38 state (folder exit 0, all-libraries
  exit 2 at zero diff, the baseline's 1 `C1083` at `opengl\wgl.cpp:31` plus 165 warning lines).
- No `winqor_gui` **code** changes: no field width, no initializer, no `static_assert`, no typedef and no call is edited;
  the six edits are comment lines only. `IconInfoEx` stays layout-identical, `ScrollInfo` keeps its two uninitialized
  fields, `WindowPlacement::length` stays uninitialized.
- The `*T` surface itself is untouched: 0 of the 64 declarations naming an SDK width token (`LPTSTR`/`LPCTSTR`/`TCHAR`,
  62 of them `T`-suffixed) changed spelling, so no mangled name moves and the published import library is unchanged.
- The other open leads stay untouched: U1, U2, U20, U27 and P3, P4, P6 remain open on their own records.

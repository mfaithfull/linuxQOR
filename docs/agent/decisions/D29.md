## D29: T9 step 9c - wrap the 4 `//System Information functions` members in a new `systeminfo.cpp` TU and put `static` on all 4 declarations - ACTION (9 Nov 2026)

Step 9c of the D26 tranche queue, executed in D26's own shape (one section, one new TU, one gate diff per session) and in
9a's `strings.cpp` / 9b's `rawinput.cpp` / T6's `listbox.cpp` shape: the new TU and the header edit land together, closing
U4's link half (a caller of any of the 4 failed at `LNK2019`) and U18's non-static half in one step. Nothing here is re-derived:
the 4 members, their `um\WinUser.h` declaration lines, their ordinals/hints, their guard stack and their prototypes were
measured once this session by `_tmp_t9_9c_measure.ps1`, `_tmp_t9_9c_sdkctx.ps1`, `_tmp_t9_9c_blocks.ps1`,
`_tmp_t9_9c_sal.ps1`, `_tmp_t9_9c_shrink.ps1` and `_tmp_t9_9c_bypassw.ps1`, and that table is the source of every figure below.

### What landed

### Binding spelling - the AW form is load-bearing for 1 of the 4, and forbidden for the other 3

**3 x bare `qor_pp_useswinapi(user32, <literal>)` and 1 x `qor_pp_useswinapiAW(user32, SystemParametersInfo)`** - the same
split D28 argued for 9b's 6/1 and D27's 9a needed 34/0. `SystemParametersInfo` is one of the two A/W-only stems left in the
remaining population (the third, `GetRawInputDeviceInfo`, went in at 9b). The stem macro switch is verbatim
`um\WinUser.h:13268`-`:13272`: `#ifdef UNICODE` / `#define SystemParametersInfo SystemParametersInfoW` / `#else` /
`#define SystemParametersInfo SystemParametersInfoA` / `#endif`, and `user32.h:15` `#undef`s that stem before the class is
declared. The loaded export table (`_tmp_user32_exports.txt`, 1,018 names, re-checked this session with
`_tmp_t9_9c_measure.ps1`) reads **no row for the stem `SystemParametersInfo`** and rows `SystemParametersInfoA` hint `3A8`
(ordinal 2430) / `SystemParametersInfoW` hint `3AA` (ordinal 2432) - and no row for `SystemParametersInfoEx`/`ExA`/`ExW`
either. A bare binding therefore stringizes a name `user32.dll` never exported (G2), caches a NULL `pFunc` for the process
lifetime and throws on every call (G5). The other 3 literals are export rows - `GetSysColor` `1C5` (1957), `GetSystemMetrics`
`1C9` (1961), `SetSysColors` `368` (2372) - and none has an A/W sibling, so `qor_pp_useswinapiAW`, which pastes `Stem ## W`
at `kernel32.h:77`, would bind `GetSysColor` to the non-existent export `GetSysColorW` (the table's neighbour is
`GetSysColorBrush` `1C6`, not `GetSysColorW`).

`cl /EP` on this TU resolves **5** `GetProcAddress` sites, of which **4** are this TU's: literals
`"GetSysColor"` `"GetSystemMetrics"` `"SetSysColors"` `"SystemParametersInfoW"` against the module literal `L"user32"`
(`GetModuleHandleW(( ( L"user32" ) ))` on every row). The bare stem and `SystemParametersInfoA` read 0 - the AW form pastes
the W spelling, which is the point of the note above. The 5th site is not this TU's: it is `user32.h:840`'s header-inline
`wsprintfT` member (D20) binding `"wsprintfW"`, inherited through the include, and it is the same 5th row D28 recorded for
9b. `_tmp_t9_9c_epcheck.ps1` prints `code_bindings_bare=3 code_aw=1 code_library_call=4 code_other_call_forms=0

SetSysColors=1 SystemParametersInfoW=1 SystemParametersInfoA=0 SystemParametersInfo=0` from the `/EP` capture.

Declaration lines in `um\WinUser.h` 10.0.26100.0 (`_tmp_t9_9c_sdkctx.ps1`, printed context, and `_tmp_t9_9c_measure.ps1`'s

`#if :9685`); `GetSystemMetrics` shares that stack with `#ifndef NOSYSMETRICS` (`:7242`) in place of NOCOLOR and DESKTOP at

(`kernel32.h:22-30`, `_WIN32_WINNT`/`WINVER` `0x0A00`) is the live condition and the section needs no guard of its own. None
was added.

### Signatures - D18, and the header edit is therefore `static` only

All 4 declarations already copy the prototype of the export their member binds - types, parameter names and order. The SDK
spells them `GetSysColor( _In_ int nIndex)`, `GetSystemMetrics( _In_ int nIndex)`,
`SetSysColors( _In_ int cElements, _In_reads_(cElements) CONST INT * lpaElements, _In_reads_(cElements) CONST COLORREF *
lpaRgbValues)` and the shared `SystemParametersInfoA`/`W` shape `BOOL WINAPI (UINT uiAction, UINT uiParam, PVOID pvParam,
UINT fWinIni)`; the header already spells the two `SetSysColors` pointers lowercase `const`, so D18's signature check passes
with no move and no U23-style const-on-pointer fix is owed.

### SAL and return conventions (U1/U2/U7) - 0 of the 5 prototype blocks carry `_Check_return_`

`_In_` on the two index members, `_In_reads_(cElements)` on both `SetSysColors` arrays (`:9708`/`:9709` - the SDK's own
statement that the element count and the two arrays agree, which this layer forwards rather than checks) and
`_Pre_maybenull_ _Post_valid_` on `SystemParametersInfo`'s `pvParam` (`:13257`/`:13266` - NULL is a legal payload for the
actions that take none). **2 of the 5 do carry `_Success_(return != FALSE)`** - `SystemParametersInfoA` `:13251` and
`SystemParametersInfoW` `:13260` - so FALSE is the SDK's own statement of failure there, while `GetSysColor`/`GetSystemMetrics`/
`SetSysColors` carry no such claim. The TU still has **0 `Win32ErrorHandler` and 0 `CheckReturn`**: the session-27 soundness
test ("only sound where the SDK's failure value is not also a legal success value") bars a zero-check at `GetSysColor` (a
`COLORREF`, and 0 is a colour) and at `GetSystemMetrics` (a metric in pixels, and 0 is a legal metric) - the same test D28
applied to 9b's 6 numeric returns - and adopting `CheckReturn` for the `BOOL` pair would change run-time behaviour rather
than mirror the SDK (G6: `returncheck.h:19` always selects the checked wrapper type). Every value comes back as the OS wrote
it, which is what leaves a swallowed SEH fault and a legitimate 0 indistinguishable to the caller (U7).

## D39: U10 - the console-internal surface is documented by Microsoft, the block is verbatim - POLICY (10 Nov 2026), CLOSES U10, NO CODE CHANGE

Decision (user, 10 Nov 2026): the "no Microsoft authority" premise of U10 is false - the console-internal types are documented at **https://learn.microsoft.com/en-us/windows/console/consolecontrol** ("ConsoleControl function - Windows Console", **Last updated on 2023-07-12**), which also notes the lack of an import library. U10 closes on that authority with **no code change** - the same shape U7 (D35) and U5 (D36) closed on, and U9 closed with.

Measured against that page (10 Nov 2026, nothing inherited; probe `tmp/_tmp_u10_cmp3.ps1` over `tmp/_tmp_u10_msdoc.txt`, a verbatim copy of the page's typedef block):

- **The type block is verbatim.** `user32.h:23`-`66` joined and whitespace-normalised is **`-ceq`** (case-sensitive) to the page's six typedefs normalised the same way: **819 characters both sides, equal = True**. Same six typedefs, same order, same member names and types, same trailing comma after `ConsoleEndTask`, and the page itself spells the SAL-annotated members as `IN DWORD dwProcessID;` / `IN HWND hwnd; IN RECT rc;` - the `IN` tokens at `user32.h:58`-`65` are **Microsoft's own spelling**, not a project invention.
- **The signature matches the documented one exactly.** Header `user32.h:814`: `static NTSTATUS ConsoleControl(CONSOLECONTROL Command, PVOID ConsoleInformation, DWORD ConsoleInformationLength);` vs page `NTSTATUS ConsoleControl( _In_ CONSOLECONTROL Command, _In_reads_bytes_(ConsoleInformationLength) PVOID ConsoleInformation, _In_ DWORD ConsoleInformationLength );` with the SAL annotations stripped: identical parameter names, types and order; the only difference is the header's `static` classifier, the folder's own convention (U4's census, 600 `static` / 0 non-static). D18's "a wrapper's signature mirrors the export" is now **verified** for this member.
- **Fresh export row** (`dumpbin /exports C:\Windows\System32\user32.dll` -> `tmp/_tmp_u10_exports.txt`, DUMP_EXIT 0): exactly **one** row matches - `1594   55 00028FD0 ConsoleControl`. No `ConsoleControlA`/`ConsoleControlW` row, so the bare `qor_pp_useswinapi` at `console.cpp:39` is right (D13) and the page's "available as the resource named ConsoleControl in User32.dll" names the same export the binding asks for.
- **Pairing is complete, no orphan type.** The page pairs each command with exactly one structure - `ConsoleNotifyConsoleApplication` -> `CONSOLE_PROCESS_INFO`, `ConsoleSetCaretInfo` -> `CONSOLE_CARET_INFO`, `ConsoleSetForeground` -> `CONSOLESETFOREGROUND`, `ConsoleSetWindowOwner` -> `CONSOLEWINDOWOWNER`, `ConsoleEndTask` -> `CONSOLEENDTASK`. 5 commands, 5 structures, 0 orphan, 0 unpaired: the header carries exactly the documented set.
- **Enum numbering is as documented.** The page spells the enum with no explicit values, so the numbering is the implicit 0..7 of the documented order (`Reserved1` 0, `ConsoleNotifyConsoleApplication` 1, `Reserved2` 2, `ConsoleSetCaretInfo` 3, `Reserved3` 4, `ConsoleSetForeground` 5, `ConsoleSetWindowOwner` 6, `ConsoleEndTask` 7). The header's order is identical, so the numbering matches the authority, and the three `Reserved*` holes are **Microsoft's own names**.

What the authority settles, item by item:

- **U10 (i)** "no Microsoft authority, layout and enum numbering unverifiable locally" - **gone**: the page gives the layout verbatim and the header matches it character-for-character.
- **U10 (ii)** `Reserved1`/`Reserved2`/`Reserved3` as unqualified global enumerators - **not a defect**: the page's Remarks say "This function is not defined in an SDK header and **must be declared by the caller**", and its metadata reads "Header none, see remarks / Library none / DLL User32.dll". Declaring them at global scope in a published header **is** what Microsoft prescribes; namespacing them under `qor::win::api` would break the verbatim match with the documented surface, so the documented spelling is kept.
- **U10 (iii)** the `IN` macro dependency - **settled by the header itself**: the page spells `IN`, and `user32.h:7` includes `kernel32.h` (which pulls `<Windows.h>` and the annotation headers) **before** the type block, so the dependency is satisfied by the header's own first line, not by a consumer's include order. Spelling `IN` out would deviate from the verbatim copy.
- **Corroboration for other records:** the page's "This function has **no associated import library** ... You must use the LoadLibrary and GetProcAddress functions to dynamically link to User32.dll" is the Microsoft authority behind `qor_pp_useswinapi` = `GetModuleHandle` + `GetProcAddress` (`kernel32.h:75`) and behind `user/CMakeLists.txt:66` / `kernel/CMakeLists.txt:17` carrying 0 import-lib entries - the design D36 accepted for U5 is the mechanism Microsoft mandates for this export. The page's return semantics (`STATUS_SUCCESS`, only negative is failure) match `console.cpp`'s banner claim that `== 0` is not a valid failure test, so U2's settled no-`CheckReturn` policy stays.
- **Guard level:** the page requires Windows 7 / Server 2008 R2 minimum, "[desktop apps only]", so no SDK guard exists and none is wanted; under the D21 pin (`_WIN32_WINNT`/`WINVER 0x0A00`, `NTDDI_VERSION 0x0A000010`) the unconditional declaration at `user32.h:814` is correct.

One correction this records rather than applies: `console.cpp:17`-`23` (a **frozen** review banner, protocol v3 - never edited) states "there is no Microsoft prototype to pair this signature against, and the export table is the only authority for the name". With D39 that is stale - the page **is** the prototype authority. The correction lives here and in `registers/u10.md`, not in the TU.

What D39 does not do:

- **No file in `src` changes.** `user32.h` stays 819 lines with the block at `:23`-`66`, `console.cpp` stays as it is, and no citation comment is added to either (the precedent U9 set: no header comment required). No gate diff is therefore in play - both gates remain at their D38 state (folder exit 0, all-libraries exit 2 at zero diff).
- No namespace, no `IN` spelling change, no drop of the console-internal surface - the documented set is kept, per D18.
- U10's stale line cites (`user32.h:19-62`, `console.cpp:19`) stay stale by design under protocol 7; the block now reads `:23`-`66`.
- U17's A/W census, U21's section grouping and U27's `STRICT` name question are untouched - `ConsoleControl` has no A/W family and no `T` suffix, which the fresh export row confirms rather than assumes.

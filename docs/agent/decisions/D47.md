### The ownership taxonomy the notes carry (the reason this item is not a one-line fix)

A Windows handle is a value, not an owner, so "who must close this" is a property of the call that produced it, and **the release verb is per family, not `Close`** - the states and the verbs are stated in the two header notes and referenced from the rest:

- **Must be released** (this process owns it): `CreateCursor`, `LoadCursorFromFileT`, `CopyCursorT` -> `DestroyCursor` (`user32.h:391`); `CreateIcon`, `CreateIconFromResource`, `CreateIconFromResourceEx`, `CreateIconIndirect`, `CopyIcon` -> `DestroyIcon` (`:438`).
- **Must never be released** (the OS owns it): `LoadCursorT` and `GetCursor` return shared system handles; `LoadIconT` returns one shared handle (measured 1 Nov 2026, session 18: `LoadIconW(NULL, IDI_APPLICATION)` -> `0x1002B`, the same value every load, the predefined ids are not handle-table entries at all); `SendMessageT`'s `BM_GETIMAGE`/`BM_SETIMAGE` returns are the window's.
- **Releasable but not yet** (ours, still live elsewhere): a handle stored in a `WNDCLASS`/`WNDCLASSEX` or set as the system cursor while another holder still reads it - the `windowclass.cpp:123-126` site.
- **Released by a verb that is not `Close`**: `HWND` -> `DestroyWindow` (`user32.h:152`), `HDC` -> `ReleaseDC` (`:339`, and the pair must match - the U22 instance), `HMENU` -> `DestroyMenu` (`:227`), `HACCEL` -> `DestroyAcceleratorTable` (`:428`), `HENHMETAFILE` -> `DeleteEnhMetaFile` (`gdi32.h:251`), `HIMAGELIST` -> `ImageList_Destroy` (comctl32), `HHEAP` -> `HeapDestroy` (kernel32). `CloseEnhMetaFile` (`gdi32.h:245`) and `CloseMetaFile` (`:246`) **create**, and `ShutdownBlockReasonDestroy` (`user32.h:671`) destroys nothing - which is why "Close" is not a rule any consumer here can apply.
- **Absorbed by the OS**: a violated contract may be tolerated silently (`DestroyIcon` on a shared handle returns 1 with `GetLastError` 1402 `ERROR_INVALID_HANDLE`, and `GetIconInfo` on that handle still succeeds) - so a wrong ownership decision is often invisible, which is why these findings were measured rather than inferred.

### Why the fix is not in winqor_api_user's hands

- Every wrapper the item names is a faithful pass-through: `DestroyCursor`/`DestroyIcon` forward their argument verbatim (the bindings at `api_layer/user/cursor.cpp:77` and `api_layer/user/icon.cpp:108`), `ShowCursor` returns the SDK's `int` count, `LoadCursorT`/`LoadIconT` return the SDK's `HCURSOR`/`HICON`. Nothing a wrapper does chooses who owns the value it returns.
- The wrong decisions are made at the call sites: the `own = true` default on the two published ctors, the four `ButtonController` sites that omit the flag, the `WindowFactory` temporaries, the `WindowClass` handle copies. Changing any of them is a behaviour change in `winqor_gui` - the standing rule U20 states, the arm U19 closed on at D41, U22 at D43 and U26 at D45.
- `PrimitiveHandle` has no release/reset API (`common/handles/handle.h:9-47`), so no consumer can clear the member before its destructor; adding one changes `winqor_wincommon`'s published interface and every consumer's ownership contract.
- No hook, import-library entry or binding in this library can redirect a `DestroyCursor`/`DestroyIcon` call a `winqor_gui` translation unit already issues through its own destructor.

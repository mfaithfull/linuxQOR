# D43 - U22: the NULL-HWND ReleaseDC note goes where the error is; U22 closes cannot-be-fixed-in-this-library - POLICY (11 Nov 2026), CLOSES U22, NO CODE CHANGE

The decision, from `docs/agent/decisions/D43.md` (user, 11 Nov 2026): U22 lands as a **note in the source where
the error actually is** - a 25-line comment block immediately above `DeviceContext::Release()` in
`src/platform/os/windows/ui/gui/gdiobjects/devicecontext.cpp`, the one member that issues the `User32::ReleaseDC`
call - and closes as **cannot be fixed within `winqor_api_user`** (the standing U20 rule, the D41 arm).

- **The route the note states**: handle ctor -> `m_hWnd == 0` -> `MustRelease()` -> `~DeviceContext` ->
  `ReleaseDC(NULL, hdc)`; three `WindowController` sites take it (`GetADC()`, `GetADC(rgn, flags)`, `GetDC()` set
  `MustRelease()` without ever setting `m_hWnd`); the SDK contract makes the NULL call return 0 and leave the DC
  unreleased; the built `examples/.../mainwindow` caller makes it reachable; `PaintSession` is the one correct
  consumer (never sets `MustRelease`).
- **Why not here**: `User32::ReleaseDC` forwards its arguments verbatim through `Library::Call<int, HWND, HDC>` -
  it never invents or recovers an `HWND`, and the `DeviceContext` reaching it was built from a bare `HDC`; fixing
  the pairing means editing `winqor_gui`'s ownership contract, another library's behaviour change.
- **Comment-only**: no token, declaration, call or build input changes; `winqor_gui` behaviour unchanged; both
  gates stay at their D38 state; nothing in `registers/u22.md` is re-audited - its stale cites are carried into
  the note exactly as written (protocol 7).
- Stale when the note is removed from `devicecontext.cpp`, a `WindowController` site starts carrying the `HWND`,
  or the frozen register's cites are re-measured as if current.

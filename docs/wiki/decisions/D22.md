# D22 - T1: the Authorization pair defined in a new `security.cpp` TU and made `static` - ACTION (8 Nov 2026)

The decision, from `docs/agent/decisions/D22.md` (user decision, 8 Nov 2026): **add the two
definitions, do not delete the declarations.** The T1 pair `GetUserObjectSecurity` /
`SetUserObjectSecurity` (`user32.h:760-761`, declared non-static and defined nowhere, so any
caller failed at `LNK2019`) gets a NEW `security.cpp` TU - not `desktop.cpp`, which the T1 note
named as the natural home for the rest of the user-object family; the Authorization section is
kept separate - and `static` goes on both declarations to match the folder's static majority.

- Each definition is bound bare `qor_pp_useswinapi` (both are single-stem `user32.dll` exports,
  1DB / 375, no A/W sibling) and copies the `winuser.h` prototype parameter-for-parameter (D18).
- What it settles: for this pair the U4 declared-but-undefined shape is gone (a caller links) and
  the U18 non-static shape is gone; U4 and U18 stay open folder-wide. The census moves static
  534 -> 536 / non-static 99 -> 97 and bindings 535 -> 537, but **coverage is unchanged at 757 of
  1,018** - the instrument counts a member declaration and the pair was already declared, so this
  was a link gap, never a coverage gap (the arithmetic D24 later states outright for T6).
- Recorded gate: `security.cpp` standalone at `/W4` exit 0, folder 46/46 at `/W4` clean, `cl /EP`
  resolving exactly the two binding literals against module literal "user32", and the shared-header
  `user32.h` edit diagnostic-neutral against the standing 113-source baseline (set-difference
  0 new / 0 gone).
- Stale when `security.cpp` drops out of `CMakeLists.txt`, the `static` at `user32.h:760-761`
  disappears, or a later decision deletes the pair; the folder gate re-run falsifies all three.

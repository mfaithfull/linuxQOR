# D44 - U24: FlashWindow misread fixed by hand in the gui layer - a named single-point exception to U20 - POLICY (11 Nov 2026), CLOSES U24

The decision, from `docs/agent/decisions/D44.md` (user, 11 Nov 2026): U24's defect - `WindowController::Flash`
presenting `FlashWindow`'s previous-active-state `BOOL` as a "did it work" result - is **fixed by hand in
`winqor_gui`**, the register's way-out #3. This is recorded as a **single-point exception**: the U20 rule
(record, don't perform, gui-side fixes - the arm D41/D43 closed on) stays in force everywhere else.

- **The artefact**: the `Flash` body at `src/platform/os/windows/ui/gui/controllers/windowcontroller.cpp:715-724`
  builds `FLASHWINFO` (`cbSize = sizeof(FLASHWINFO)`, `hwnd = WINDOW_HANDLE`, `uCount = 1`, `dwTimeout = 200`,
  `dwFlags = invert ? FLASHW_ALL | FLASHW_TIMERNOFG : FLASHW_STOP` - the SDK's field spellings) and returns
  `User32::FlashWindowEx(&flashInfo)`'s success `BOOL`, so the method's `bool` finally means what it claims.
- **The wrapper does not move**: `User32::FlashWindowEx(::PFLASHWINFO)` at `errorhandling.cpp:70` / `user32.h:681`
  is a faithful pass-through; 0 `winqor_api_user` sources touched, `user32.h` stays 819 lines / 600 members / 599
  bindings.
- **Collateral recorded, not fixed**: the `FlashWindowEx` wrapper carries no `CheckReturn` (a U2 policy gap, G6);
  `FLASHWINFO` is under `#if(WINVER >= 0x0500)`, so the call site needs the U16 guard the gui build already has;
  `registers/u24.md` carries only its head closure line (protocol 7).
- **No gate is run**: the edit is in `ui/gui` (`winqor_gui`), outside both `cl` gates, which stay at their
  post-D38 state.
- Stale when the `Flash` body stops calling `FlashWindowEx`, the FLASHW flags change meaning, or the exception
  is cited to justify a second direct gui edit without a decision naming it.

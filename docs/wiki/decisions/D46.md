# D46 - U27: the STRICT arm decides the published name; the layer publishes STRICT and does not override NO_STRICT - POLICY (11 Nov 2026), CLOSES U27

The decision, from `docs/agent/decisions/D46.md` (user, 11 Nov 2026), an invariant now in force: **the QOR
Windows api_layer publishes the `STRICT` arm, and does not override a consumer's `NO_STRICT`** - handles as
opaque struct pointers, `HOOKPROC` as the typed `CALLBACK`; a `NO_STRICT` consumer gets that arm's types and
names, and the mismatch is recorded, not fixed. The third axis of the same family as the D21 version pin and
the D45 no-`/DUNICODE` close.

- **Mechanism read on disk** (Kits 10.0.26100.0): `minwindef.h:21-25`/`ntdef.h:785-789` set `STRICT` unless
  `NO_STRICT` was defined first; `ntdef.h:851-861` switches `DECLARE_HANDLE` between per-type struct pointers
  and `void *`; C++ mangling encodes the pointed-to type, so published names move with the arm.
- **Measured** (seven probe legs, recorded exit codes): the built tree is already STRICT (P1 exit 0); a consumer
  can reach `NO_STRICT` (P2); the `#undef` lever works only **before** the include (P3) and is order-dependent
  after (P4); the four hook members' `dumpbin /symbols` names differ 3 of 4 across the arms while
  `CallMsgFilterT` stays identical; forcing STRICT on a `NO_STRICT` consumer breaks **its own** handle
  inter-conversion with `C2440` (P6); a guarded `#define STRICT 1` (P7) forces the arm without erasing the
  consumer's macro but is still order-dependent.
- **Blast radius**: 390/600 members name an `H`-type, 382 name a non-`HANDLE` arm-sensitive type, 3 name
  STRICT-sensitive callback typedefs (`DrawStateT`, `SendMessageCallbackT`, `SetWindowsHookExT`) - roughly two
  thirds of the published surface; **0 in-tree callers** of the hook family, so U27 is a property of the
  published surface, not a performed defect.
- **Why the `#undef` at `kernel32.h:36` is not the fix**: inert (the macro is defined nowhere, gates byte-identical -
  the diff is the signal), order-dependent, moves the failure into the consumer (P6), and erases a consumer-set
  knob against D21's assert-don't-clobber precedent; retyping to arm-stable types would break D18/D25.
- **Residual stays recorded**: a third-party TU that defines `NO_STRICT` and reaches `<windows.h>` first gets
  its own arm - the same unfixed class D21 and D45 left.
- Stale when a QOR build input grows a `/DNO_STRICT` or `/UNO_STRICT` flag, the layer gains a `#undef NO_STRICT`,
  or an affected member's published signature retypes away from the SDK arm.

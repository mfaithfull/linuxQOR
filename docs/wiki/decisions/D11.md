# D11 - Variant API wrapper for header-inline Windows API entry points - RULE (26 Oct 2026)

The decision, from `docs/agent/decisions/D11.md`: classify every declared api_layer entry point as
**(E)** export-bound (`qor_pp_useswinapi` + `Library::Call`) or **(I)** header-inline (the SDK
header supplies the definition; the wrapper calls it directly at compile time, never
`Library::DefProc`/`GetProcAddress`). Decide (E) vs (I) from the header text, not from dumpbin.

- Implemented, not just designed: `library.h` gains `inlineCall`/`voidInlineCall` with the same
  `__try`/`__except` guard; `kernel32.h` gains the `qor_pp_usesinlineapi` marker; `kthreadpool.cpp`
  gains the six wrappers. `SetThreadpoolCallbackPersistent` and `SetThreadpoolCallbackPriority` are
  declared, marked header-inline, and deliberately **left unwrapped** (WINAPI_FAMILY portability) -
  the one open review call the entry records.
- Feasibility was proven by `tmp/_tmp_inline_probe*` (`cl /c` exit 0, zero undefined Threadpool/
  `Tp*` externals) and the rebuilt audit (`implemented=368 header_inline_nonexport=2 missing=0
  total=370`) - throwaway probes, so the page carries the D56 sentinel.
- Stale when the SDK headers move or a wrapper is wired for the two gap names; the entry also
  records an audit trap (impl paths must be relative with forward slashes).

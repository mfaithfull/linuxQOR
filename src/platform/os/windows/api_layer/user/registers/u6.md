# U6 register entry (verbatim)

- **U6 - calling-convention mismatch in the call path: RESOLVED 1 Nov 2026 (off-protocol item fix, not a TU session).**
  Measured 29 Oct 2026. The first half was `library.h:16` `typedef int(__stdcall *DefProc)(void);` (committed in user
  commit `89da3452`). The second half is now fixed: `Call` builds `typedef ret(__stdcall *fPtr)(MethodArgs...)`
  (`library.h:46`) and `voidCall` builds `typedef void(__stdcall *fPtr)(MethodArgs...)` (`library.h:68`), so the pointer
  the entry point is called through carries the same convention as `DefProc` and as the `WINAPI` export it names.
  `__stdcall` is spelled out, not `WINAPI`: that is what `DefProc` at `:16` already uses, and `library.h` cannot assume
  an SDK header is in scope (`WINAPI` would be undefined in a TU that includes `library.h` first).
  **Measured evidence** - `tmp/_tmp_u6_cc_probe.cpp` built for **x86** by `tmp/_tmp_u6_cc_x86.bat` (x64 has one calling
  convention, which is why no x64 gate ever saw this): pre-fix the disassembly of `Library::Call<int,int,int,int>` was
  `call dword ptr [ebp-24h]` + `add esp,0Ch`, and `voidCall<int,int,int>`'s `call dword ptr [ebp-20h]` + `add esp,0Ch` -
  caller-side cleanup after a `WINAPI` callee that already returned with `ret 0Ch`, so the second cleanup pops 12 bytes
  past the arguments, i.e. the return address. Post-fix both sites are a bare `call` with no stack adjustment
  (`tmp/_tmp_u6_cc_x86_pre.asm`, `tmp/_tmp_u6_cc_x86_post.asm`).
  **Blast radius measured:** every `qor_pp_useswinapi`/`...AW` binding in the tree goes through this one path - **1,638**
  of them (user32 429, kernel32 330, gdi32 324, ole32 201, ws2_32 135, shell32 60, comctl32 53, uxtheme 48, opengl32 27,
  dwmapi 23, Xinput1_4 7, shcore 1) - and all twelve are Win32 system DLLs whose exports are `WINAPI`, so `__stdcall`
  is correct for every one. `inlineCall`/`voidInlineCall` (`library.h:98`, `:112`) are **not** instances and stay
  unqualified: their argument is the address of an SDK `FORCEINLINE` definition (`winbase.h:7915`
  `InitializeThreadpoolEnvironment` and its five siblings, no `WINAPI` in the declaration), so the default-convention
  parameter type matches and the compiler checks it at compile time. `cursor.cpp`'s TU comment (the one place in the
  folder that cites U6 as live risk) was updated with the closure.
  **Gate:** user folder **38/38** at `/W4`, exit 0, 0 diagnostics (`tmp/_tmp_cl_all_u6post.log`). New **extended gate**
  for shared-header changes - all **106** api_layer sources across the 12 libraries, `tmp/_tmp_cl_all_apiall_u6.bat`
  with the source list in `tmp/_tmp_u6_apiall_sources.rsp`: the pre-fix and post-fix logs are **byte-identical**
  (165 `/W4` warnings in `gdi`/`uxtheme` plus one pre-existing `fatal error C1083` at `opengl/wgl.cpp:31`, which cannot
  open `gdi32.h` with this cl line and is unrelated to U6), so nothing outside the reviewed folder regressed.
  **Record hygiene (measure `library.h:NNN` citations against these numbers):** the fix added 13 lines, so `library.h`
  is 114 -> **127** lines and every citation to it above the insertion point moved by 13. Measured now: `DefProc` `:16`
  (unchanged), `Call` `:44`, its throw `:52`, `__try` `:54`, `ret _{}` `:61`; `voidCall` `:66`, its throw `:84`,
  `__try` `:74`; `inlineCall` `:98`, `voidInlineCall` `:112`. At HEAD they were throw `:39`/`:71`, `__try` `:41`/`:61`,
  `inlineCall` `:85`, `voidInlineCall` `:99`. That makes two pre-existing citations wrong in a way that predates this
  fix: `u8.md:3` cites the throws at `library.h:60`, `:92` and `u1.md:9` cites `serious(...)` at `:41` - at HEAD the
  throws were `:39`/`:71` and `serious(...)` is at `:20`. Correct them in those entries' own sessions; do not
  silently edit them here.

- **U6 addendum 4 Nov 2026 (session 31, `systemshutdown.cpp`): the x86 blind spot that this item's own fix proved,
  measured folder-wide for the first time, and a `WINAPI`-on-a-member defect class closed.**
  **(a) A convention token on a `static` member definition is checked by the compiler, not ignored.** `:37`/`:44` of that
  TU spelled `BOOL WINAPI User32::ShutdownBlockReason...` while `user32.h:605`/`:606` declare the members with no token -
  the only two such heads in all 38 TUs. For **x86** MSVC fails both with `error C2373: redefinition; different type
  modifiers`; for **x64** it drops the modifier, so the emitted symbol is the same `__cdecl` decoration a consumer of the
  header reference resolves to and `dumpbin /disasm` of the object is byte-identical before and after removal
  (`tmp/_tmp_s31_winapi_probe_s31.cpp`, `tmp/_tmp_s31_winapi_s31.txt`, `tmp/_tmp_s31_x64_pre_s31.asm`/`_post_s31.asm`).
  Both heads normalized to the bare spelling - the same rule U6's fix states from the other side: the entry point's
  `__stdcall` lives in `Library::Call`'s `fPtr` and in `DefProc`, and the wrapper's own convention is the C++ one its
  in-class declaration states.
  **(b) Why no gate ever saw (a): the tree does not compile for x86 at all, and the cause is one header line.**
  `kernel32.h:92` (`static void* RtlLookupFunctionEntry(ULONGLONG, PULONGLONG, PUNWIND_HISTORY_TABLE)`) names
  `PUNWIND_HISTORY_TABLE`, which the SDK typedefs only inside
  `#if defined(_AMD64_) || defined(_ARM_) || defined(_ARM64_)` (`um/winnt.h:21939`-`:21963`, closed `:21963`) - there is no
  `_X86_` arm. Compiling every source in `tmp/_tmp_u6_apiall_sources.rsp` for x86 (`tmp/_tmp_s31_x86_apiall_s31.bat`,
  digest `tmp/_tmp_s31_x86_digest_s31.ps1`) gives **93 of 106 api_layer TUs failing with `C2061 identifier
  'PUNWIND_HISTORY_TABLE'`** - user 37/38, gdi 15/16, kernel 22/23, shell 7/8, opengl 3/4, winsock2 2/3, one each for
  comctl32/direct2d/dwm/ole32/shcore/uxtheme/xinput - and the **13 survivors are exactly the library glue TUs**
  (`winqor_api_*.cpp`), i.e. every library's public TU builds and none of its implementation does. Two follow-on errors
  are in the same line's blast radius: `kerrorhandling.cpp:97` re-declares the same signature and `:104` then fails
  `C2065 'TargetGp': undeclared identifier`, and the `opengl/wgl.cpp:31 C1083 gdi32.h` failure is the pre-existing one
  already recorded above. **Nothing was changed** - the tree is x64-only (`CMakeSettings.json:4` "x64-Debug"), the fix is
  a kernel-header decision outside this review's protocol, and the finding is recorded here because (i) it is the reason
  U6's stack corruption needed a dedicated x86 probe, (ii) it hid the C2373 pair above for 30 sessions, and (iii) any
  future x86 work must clear this one line first. Suggested follow-up for a kernel-layer session: give
  `RtlLookupFunctionEntry`'s third parameter a type the SDK defines on every arch, or guard the declaration.

- **U6 addendum status 5 Nov 2026 (user decision D17, `docs/agent/DECISIONS.md`): the x86 blocker in (b) is withdrawn as a
  blocker, and the suggested follow-up above is NOT to be actioned.** Windows support is 64-bit (amd64) only - in-tree note
  `src/platform/os/windows/purpose.md:3` - so `kernel32.h:92` stays as written and the 93-of-106 x86 `C2061` population is
  not a defect. What the addendum still stands for is the method finding: an x64 gate cannot see arch-dependent defects,
  which is why U6's corruption needed a dedicated probe and why the `C2373` pair in (a) hid for 30 sessions. That finding is
  now closed out by scope rather than by tooling: **no x86 compile is a step in any gate in this folder** (which also
  retires the "add an x86 compile" guidance at `gotchas/sessions-31-33.md:13-16`), so arch-dependent defects are prevented
  by the x64-only contract instead of being probed for.

# U18 register entry (verbatim)

- **U18 - a wrapper pair whose return type contradicts the SDK: `void` where `user32.dll` returns `BOOL`.** Opened
  30 Oct 2026 (session 8) while mapping the coordinate-transform family for `coordtransform.cpp`. `user32.h:188`
  `static void LogicalToPhysicalPoint(HWND, ::LPPOINT*)` and `:191` `static void PhysicalToLogicalPoint(HWND, ::LPPOINT*)`
  are defined `window.cpp:432-437` and `:453-458` with `Library::voidCall<HWND, ::LPPOINT>`, but the SDK declares both
  returning `BOOL` (`winuser.h:9522-9528` and `:9530-9535`, guarded `WINVER >= 0x0600`) and the export table has both as
  single exports (ordinals 26D, 2AB). `LogicalToPhysicalPoint` returns FALSE when the point is not inside a physical
  display area, which is a case the DPI-aware caller has to handle - the wrapper discards it, and the only two callers,
  `WindowController::LogicalToPhysicalPoint`/`PhysicalToLogicalPoint` (`windowcontroller.cpp:313-315`, `:328-330`), are
  `void` too, so the failure is unrecoverable all the way up. Not a run-time fault (the `voidCall` still calls through a
  correct `__stdcall` signature and the discarded `BOOL` is harmless in the ABI), so it is a surface decision rather than
  a fix: changing `void` -> `BOOL` alters an exported, called member. Also still open in the same family: the SDK's
  `LogicalToPhysicalPointForPerMonitorDPI`/`PhysicalToLogicalPointForPerMonitorDPI` (`winuser.h:9539-9552`, `WINVER >=
  0x0603`) and `WindowFromPhysicalPoint` are exported and declared at `user32.h:211` but the first two are declared
  nowhere in this library. For `window.cpp`'s session.
- **Two more U18-shaped divergences measured in `keyboard.cpp` (session 20, 1 Nov 2026), both recorded, neither
  changed.** `GetKeyboardLayoutList` returns `UINT` here (`user32.h:79`, def `:132`) against the SDK's `int`
  (`winuser.h:1313`), and `keybd_event` takes `void* dwExtraInfo` against the SDK's `ULONG_PTR` (`winuser.h:6071`).
  Both are same-width on x86 and x64, so there is no ABI effect and no run-time fault; both are published return /
  parameter types, so changing them is a surface decision like the `LogicalToPhysicalPoint` pair above. Neither shows up
  as a `sigcmp` flag - `sigcmp` compares declaration against definition and cannot see the SDK, and its one
  `keyboard.cpp` "CALL TYPE MISMATCH" at `keybd_event` is a script artefact (the site is the correct
  `voidCall< BYTE, BYTE, DWORD, void* >` at `:192`; the script compared the next function's list).
- **`mdi.cpp` (session 21, 1 Nov 2026): 0 published-type divergences.** All four members pair field-for-field with the
  SDK - `DefFrameProcA`/`W` `winuser.h:12132`/`:12141`, `DefMDIChildProcA`/`W` `:12161`/`:12174`,
  `TranslateMDISysAccel` `:12190`, `CreateMDIWindowA`/`W` `:12205`/`:12219` - return types included. Two notes from the
  comparison, both about the documentation rather than the library: `CreateMDIWindow`'s style parameter really is `DWORD`
  in this SDK (older references show `LONG`), and the SDK marks `DefFrameProc`'s `hWndMDIClient` and both
  `CreateMDIWindow` handles `_In_opt_`, which this layer spells as plain `HWND` - legal `NULL`s, unchecked (the standing
  U1/U2 policy), but no type divergence. The one type contradiction this TU did contain (`INT` in `DefFrameProcT`'s
  `Call<>` list) is **internal** - it cannot reach a caller and does not change the emitted call - so it is fixed and
  recorded under U14, not here. `DefMDIChildProcA`/`W` are also the only MDI prototypes the SDK declares as
  `LRESULT WINAPI` under `#ifndef _MAC` and `LRESULT CALLBACK` in its `#else` arm (`:12154`-`:12160`,
  `:12167`-`:12173`); irrelevant here (`_MAC` is defined nowhere in this build), but it means a `_MAC` build would see a
  different calling convention in the prototype than the `__stdcall` the wrapper calls through.

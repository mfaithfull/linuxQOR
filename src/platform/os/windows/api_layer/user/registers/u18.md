# U18 register entry (verbatim)

- **U18 - a wrapper pair whose return type contradicts the SDK: `void` where `user32.dll` returns `BOOL`.** Opened
  30 Oct 2026 (session 8) while mapping the coordinate-transform family for `coordtransform.cpp`. `user32.h:188`
  `static void LogicalToPhysicalPoint(HWND, ::LPPOINT*)` and `:191` `static void PhysicalToLogicalPoint(HWND, ::LPPOINT*)`
  are defined `window.cpp:432-437` and `:453-458` with `Library::voidCall<HWND, ::LPPOINT>`, but the SDK declares both
  returning `BOOL` (`winuser.h:9522-9528` and `:9530-9535`, guarded `WINVER >= 0x0600`) and the export table has both as
  single exports (ordinals 26D, 2AB). `LogicalToPhysicalPoint` returns FALSE when the point is not inside a physical
  display area, which is a case the DPI-aware caller has to handle - the wrapper discards it, and the only two callers,
  `WindowController::LogicalToPhysicalPoint`/`PhysicalToLogicalPoint` (`windowcontroller.cpp:313-315`, `:328-330`), are
  `void` too, so the failure is unrecoverable all the way up. Not a run-time fault (the `voidCall` still calls through a
  correct `__stdcall` signature and the discarded `BOOL` is harmless in the ABI), so it is a surface decision rather than
  a fix: changing `void` -> `BOOL` alters an exported, called member. Also still open in the same family: the SDK's
  `LogicalToPhysicalPointForPerMonitorDPI`/`PhysicalToLogicalPointForPerMonitorDPI` (`winuser.h:9539-9552`, `WINVER >=
  0x0603`) and `WindowFromPhysicalPoint` are exported and declared at `user32.h:211` but the first two are declared
  nowhere in this library. For `window.cpp`'s session.

- **`menu.cpp` (session 22, 2 Nov 2026): 0 return-type divergences, 3 parameter-type divergences.** The return half had
  never been measured per-TU because `_tmp_menu_proto_s22.ps1` printed the declaration line without the return type, which
  in `winuser.h` sits on its **own** line two above the stem - new instrument `tmp/_tmp_menu_ret_s22.ps1` reads it from

  - `TrackPopupMenu`'s last parameter is **`HWND prcRect`** (`user32.h:252`, def `menu.cpp:275`) where the SDK has
    `_Reserved_ CONST RECT *prcRect` (`winuser.h:7759-7766`). `STRICT` is on in this build (`winnt.h` defines it unless
    `NO_STRICT` - noted in session 17), so `HWND` is `struct HWND__ *` and a `RECT *` will not convert implicitly: the
    slot can carry `NULL` or a cast, nothing else. Pointer-sized both architectures, so no ABI effect and no UB, and the
    wrapper has no caller at all (U15), so it is latent on both counts.
  - `InsertMenuT` (`:184`) and `ModifyMenuT` (`:226`) take **`void* uIDNewItem`** where the SDK takes `UINT_PTR`
    (`winuser.h:7658`, `:7667`, `:7704`, `:7713`). `AppendMenuT` (`:16`) in the same section has it right, so the section
    contradicts itself; the SDK's `UINT_PTR` exists precisely so one slot carries either an item id or a string pointer,
    and `void*` forces a cast on the id case. Same width on x86 and x64, and these two **are** live
    (`ui/gui/controllers/i_m/menu.cpp:173`, `:183`), so a future signature change touches them.
  Both are published header surface (`user32.h` + definition + the matching `Library::Call<>` list, which restates the
  divergent type at `:230` and `:280`), so as with `keybd_event`'s `void* dwExtraInfo` above and with U23 they are
  recorded here for the folder-wide surface pass and **not changed in a TU session**. Parameter names also drift from the
  SDK in six wrappers (`CheckMenuRadioItem`, `GetMenuString` `nMaxCount`/`uFlag`, `HiliteMenuItem` `uItemHilite`,
  `ModifyMenu` `hMenu`, `InsertMenuItem`/`SetMenuItemInfo` `uItem`) - cosmetic, no effect, recorded once here.

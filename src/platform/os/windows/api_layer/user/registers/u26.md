# U26 register entry (verbatim)

- **U26 - `TCHAR` width is an include-order property, not a build setting.** Opened 31 Oct 2026 (session 16,
  `help.cpp`); recorded, not fixed. Measured: nothing in `cmake/`, the root `CMakeLists.txt`, `CMakeSettings.json` or
  `cmakebuild/CMakeCache.txt` defines `UNICODE`/`_UNICODE` (0 occurrences), so the only source of the define is
  `kernel32.h:7-10` under `qor_pp_unicode` (`src/configuration/configuration.h:13` = 1). `tmp/_tmp_tchar_probe.cpp` +
  `tmp/_tmp_run_tchar_probe.bat` measure both worlds in one run: with the library's include chain `_UNICODE=1`,
  `sizeof(TCHAR)=2`, `LPCTSTR==LPCWSTR`; without it `_UNICODE=0`, `sizeof(TCHAR)=1`, `LPCTSTR==LPCSTR`. Consequence: a
  consumer that sees `Windows.h` before any QOR header gets the **narrow** spelling of every published `*T` signature,
  while the built import library carries the wide one - `dumpbin /linkermember:1` shows `WinHelp` published with a
  `PEB_W` (`const wchar_t*`) - so the failure mode is a **link error** on a name that does not exist, not silent
  narrow-passing. Checked on the only consumer of the section this was found in: `ui/gui/controllers/windowcontroller.h:28-39`
  pulls in no `Windows.h`, so `winqor_gui` sees the wide spelling and `windowcontroller.cpp:795` compiles. This is the
  same one-switch property that makes the `*T` wrappers safe in `clipboard.cpp` (session 5), now stated as a library-wide
  hazard: it guards the whole `*T` surface (U17's list), and closing it means either a build-wide define (a behaviour
  decision for every consumer) or self-sufficient published headers. Related measurement folded into **U2**:
  `../returncheck.h` is included by 37 of the 38 TUs and actually used by 2 (`devicecontext.cpp` mentions it in a comment
  only; the 2 real users are `errorhandling.cpp:77-83` and `processthread.cpp:20,:29,:45`) - instrument
  `tmp/_tmp_returncheck_usage.ps1`, whose raw count over-reads comment mentions.
  **Escalated by `icon.cpp` (session 18, 1 Nov 2026): in the `GetIconInfoExT` path the include-order width is a silent
  buffer overrun, not a link error.** `winuser.h:11009`-`:11014` defines `ICONINFOEX`/`PICONINFOEX` **twice**, once under
  `#ifdef UNICODE` (`:11009`) and once in its `#else` arm (`:11012`) - measured with `tmp/_tmp_icon_type_guards.ps1`.
  `user32.h:436` takes `::PICONINFOEX`, but `qor_pp_useswinapiAW` token-pastes `GetIconInfoExW` unconditionally, so a TU
  that sees `<windows.h>` before `kernel32.h` (the only place `UNICODE`/`_UNICODE` are defined, `kernel32.h:7-10`)
  compiles the **560-byte A shape** of the parameter type against the **W** entry point, which writes **1,080** bytes: no
  compile error, no link error, just 520 bytes written past the end of the caller's struct. Measured with
  `tmp/_tmp_iconinfoex_mirror.cpp` (SDK types plus a hand copy of the caller-side mirrors) and confirmed against the real
  headers compile-only with `tmp/_tmp_iconinfoex_assert.cpp` + `tmp/_tmp_run_iconinfoex_assert.bat`
  (`assert_compile_exit=0`): in the library's own include order (`user32.h:7` pulls in `kernel32.h` first)
  `sizeof(ICONINFOEX)` = 1080 = `sizeof(ICONINFOEXW)` while `sizeof(ICONINFOEXA)` = 560, and the caller-side mirror
  `ui/gui/gdiobjects/icon.h:27-38` is field-for-field `ICONINFOEXW` (`cbSize` 0, `fIcon` 4, `xHotspot` 8, `yHotspot` 12,
  `hbmMask` 16, `hbmColor` 24, `wResID` 32, `szModName` 34, `szResName` 554) because QOR spells its own `TCHAR` from
  `qor_pp_unicode` (`common/structures.h:57-65`, `src/configuration/configuration.h:13` = 1) rather than from `_UNICODE`.
  `sizeof(ICONINFO)` = 32 = the `IconInfo` mirror at `icon.h:18-25` with the same offsets, so the two `reinterpret_cast`s
  at `ui/gui/gdiobjects/icon.cpp:89`/`:94` are layout-safe **as the tree is configured today**, and the path is
  U15-unreachable as well. This is the first U26 instance whose failure mode is corruption rather than a missing-symbol
  link error, and it is a *type* dependency, not just a name dependency: closing U26 for the `*T` surface does not close
  it unless the published headers stay self-sufficient about which `ICONINFOEX` they mean.

- **Second instance of the mirror-struct hazard, found in `ime.cpp` (session 19, 1 Nov 2026) - documentation only, no
  code change.** `SendIMEMessageEx`'s `LPARAM` is the SDK's `PIMESTRUCT` (`um\Ime.h:44-55`), and `IMESTRUCT` is named
  **nowhere** in this tree: 0 occurrences in `ime.cpp`'s preprocessed output and 0 in `src`, because `Ime.h` is never
  included (see U16's session-19 entry). A caller of this wrapper therefore has to hand-build a mirror of a struct whose
  layout nothing checks, and whose A/W flavour - like the `IMEPROA`/`IMEPROW` pair at `um\WinNls32.h:37-52`, where the
  payload fields are `BYTE[50]`/`WCHAR[50]` arrays - is decided by the same `UNICODE` include-order property this entry is
  about. There is not even a `static_assert` available as a guard, since the real type is not visible. Same class as the
  `ICONINFOEX` overrun that escalated this item in session 18: the wrapper's own signature matches the export exactly, the
  risk is entirely in the caller's reconstruction of the payload type. Recorded in `ime.cpp`'s TU comment.

- **`keyboard.cpp` (session 20, 1 Nov 2026): the `*T` surface again, measured.** 5 of the section's 7 A/W wrappers take
  a `TCHAR`-derived parameter and so depend on the include-order width: `GetKeyboardLayoutNameT(LPTSTR)` `user32.h:80`,
  `GetKeyNameTextT(int, LPTSTR)` `:83`, `LoadKeyboardLayoutT(LPCTSTR, UINT)` `:88`, `VkKeyScanT(TCHAR)` `:103`,
  `VkKeyScanExT(TCHAR, HKL)` `:104` (`MapVirtualKeyT`/`MapVirtualKeyExT` are `UINT`-typed and unaffected). In this TU the
  width is the wide one - the chain is `configuration.h` -> `user32.h` -> `kernel32.h:7-10`, which defines
  `UNICODE`/`_UNICODE` before `<Windows.h>` at `:12` - so `LPCTSTR` is `LPCWSTR` and matches the `*W` export the AW macro
  pastes. This session's three P1 fixes make the mismatch **sharper, not softer**: before them the binding asked for a
  name that did not exist and threw before any argument was marshalled, so a narrow-width consumer could not reach the
  call at all; now the call happens, and a consumer that saw `<windows.h>` first still fails at the link on the narrow
  spelling (`W6`-style `?VkKeyScanT@...` name mangling is by parameter type), not silently. Note `VkKeyScanT(TCHAR)` is a
  worse case than the pointer forms: with `_UNICODE=0` `TCHAR` is `char` and `VkKeyScanA` takes `char`, so the *narrow*
  spelling is the semantically right one while the binding is the `W` one - the wrapper is only coherent in the wide world.
- **Third instance of the mirror-struct hazard, measured 1 Nov 2026 (session 21, `mdi.cpp`): `Message` against `MSG`, and
  the mirror is only ABI-correct on x64.** The tree's only compiled MDI-adjacent call site hands a `Message*`
  (`ui/gui/view/handlers/message.h:33-44`) to the export as `::LPMSG`. `tmp/_tmp_msg_mirror_s21.cpp` puts that mirror and
  its `Point` (`ui/gui/view/drawing/point.h:31-35`, `long m_x`/`m_y`) next to the SDK `MSG` (`winuser.h:1877-1887`) and
  prints both layouts; `tmp/_tmp_msg_mirror_s21.bat` builds and runs it for **x64 and x86** (the first two-arch layout
  measurement of this review). **x64: identical** - 48 bytes each, `hwnd`/`message`/`wParam`/`lParam`/`time`/`pt` at
  0/8/16/24/32/36, `pt.x`/`pt.y` at 36/40. **x86: divergent from `lParam` on** - `MSG` is 28 bytes with
  `lParam@12 time@16 pt@20`, the mirror is 40 bytes with `lParam@16 time@24 pt@28`, because it spells `wParam`/`lParam` as
  portable `unsigned long long`/`long long` where the SDK uses the 4-byte `WPARAM`/`LPARAM`, and 8-byte alignment then
  pushes every later field. The mirror's field list is otherwise faithful to `MSG`, including the SDK's own `#ifdef _MAC`
  `lPrivate` (`winuser.h:1884-1886`). **This is not a one-wrapper problem**: the same mirror feeds seven call sites into
  six wrappers - `messagehandler.cpp:136` (`DispatchMessageT`), `:146` (`GetMessageT`), `:181` (`PeekMessageT`), `:236`
  (`TranslateMessage`), `:241` (`TranslateMDISysAccel`), `windowcontroller.cpp:658` and
  `ui/gui/view/handlers/acceleratortable.cpp:83` (`TranslateAcceleratorT`) - and `GetMessage`/`PeekMessage` **write** the
  struct, so on a 32-bit target the export would fill a 28-byte `MSG` while the caller reads a 40-byte `Message`: wrong
  `lParam`, wrong `time`, wrong `pt`, and no compile error. Only x64 is configured (`CMakeSettings.json` has the single
  `x64-Debug` profile), so the exposure is latent, not live. Recorded, not fixed: repairing it either changes a published
  `winqor_gui` header to SDK-width fields or pins the x64-only contract with `static_assert`s in the mirror's own header -
  both are surface decisions, and the wrappers that actually pass the mirror belong to `message.cpp` (session 23), where
  this entry should be picked up. Instrument pair added to `method.md`.

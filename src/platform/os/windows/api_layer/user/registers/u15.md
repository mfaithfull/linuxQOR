# U15 register entry (verbatim)

- **U15 - wrappers that are exported through `QOR_WINAPIUSER` but have no reachable caller in the tree: CLOSED by user
  decision, 2 Nov 2026 (policy - **D14** in `docs/agent/DECISIONS.md`).** Being exported and unused is **not a finding
  for this review**: the wrapper is defined, linked and callable, so the exported surface is the surface this module
  intends to publish, and whether the tree exercises it is a consumer-side (`winqor_gui`) question rather than a defect
  in this layer. The item stops at the sessions-1-22 state and **sessions no longer record U15 instances** - no per-TU
  tally, no session-log column, no append to this entry. Reachability is still established where another item's severity
  depends on it (whether a P1/P5 mis-binding is latent or live, U18's divergent `TrackPopupMenu` parameter, U19's
  LAYER-vs-BYPASS split), and such a fact is recorded in that item, not here. The item was opened 29 Oct 2026
  (session 4, user decision) so that the observation was collected in one place rather than repeated per TU. A wrapper
  counted when nothing in `src`/`examples`/`test` could reach it, including the case where its only consumer is itself
  never called (name that consumer one level deep and stop - whether the gui side should call it is a `winqor_gui`
  question, and the `Caret` controller is already documented at `docs/ui/windows/30-controllers.md:503-512`). These were
  **not dead code**: the TU is in `add_library`, the class carries `qor_pp_module_interface(QOR_WINAPIUSER)`, so the
  wrapper is part of the published DLL surface. The distinction that matters for the audit is U4's: a U4 member has no
  definition at all, so a caller gets `LNK2019`; a U15 wrapper is fully defined, linked and callable - the tree just
  never calls it. **Session 8 found the first exception in the reviewed set:** all three `coordtransform.cpp` wrappers
  are called in-tree
  (`windowcontroller.cpp:643` `ClientToScreen`, `:648` `ScreenToClient`, `:653` `MapPoints` -> `MapWindowPoints`) and
  reachable one level up (`windowimpl.cpp:1657` in `WindowImpl::GetPos`, `:2218` in `WindowImpl::SetCursorPosWin32`), so
  the `GetDCEx` mis-binding was a live defect in shipped paths, not a dead-code curiosity. That makes liveness worth
  checking before assuming a wrapper's behaviour cannot be observed.
